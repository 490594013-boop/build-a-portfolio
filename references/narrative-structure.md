# 叙事骨架与页面清单

> **先读 [narrative-archetypes.md](./narrative-archetypes.md)。**
> 同一个项目用不同原型当主线，能排出完全不同的作品集 —— 先把候选方案给用户选完，再用这里的骨架落地。

## 七段叙事

```
问题  →  方法  →  应用  →  成果  →  延伸  →  复盘  →  沉淀
```

这条弧线回答面试官心里的三个问题：

| 段 | 面试官的疑问 | 你要证明的 |
|---|---|---|
| 问题 | 这事有什么难的？ | 你能识别真问题（而不是做需求翻译） |
| 方法 | 你怎么想清楚的？ | 你有可复用的方法论（而不是凭感觉） |
| 应用 | 你怎么落地的？ | 你能做交互细节、能平衡约束 |
| 成果 | 有效果吗？ | 有可量化结果 |
| 延伸 | 还看到什么？ | 你有前瞻性（AI、新能力） |
| 复盘 | 有什么局限？ | 你诚实、有自省（**最能拉开差距**） |
| 沉淀 | 留下了什么？ | 你能抽象成可迁移的判断 |

## 15 页标准清单

| # | 页面 | 一句话职责 | 必备要素 |
|---|---|---|---|
| 0 | 封面 | 让人 10 秒知道这是什么项目 | 标题、价值主张、「周期 / 角色 / 关键词」 |
| 1 | 业务背景与挑战 | 说明难度，建立可信度 | 业务是什么 + 2~3 条真实困难（越具体越好） |
| 2 | 方法与策略 | 给出你的方法论 | 方法的三个步骤 + "为什么它不是拍脑袋" |
| 3 | 归纳 · 人与物 | 展示你如何拆解对象 | 静态要素拆解，每条事实要落到「对设计的影响」 |
| 4 | 归纳 · 人与物的交互 | 展示流程全貌 | 阶段流程 + 标注每阶段「人工 / 系统」 |
| 5 | 假设 · 痛点与机会点 | 展示你的洞察 | 每阶段：需求 → 痛点 → 机会点（判断） |
| 6 | 演绎 · 机会点→方案 | 展示收敛能力 | N 条判断 → M 个方案方向（N≥M 是加分项） |
| 7A–7D | 各方案详情 | 展示落地细节 | 四段式：痛点 → 影响 → 方案 → 结果 |
| 8–9 | 延伸（如 AI） | 展示对新能力的判断 | 变化前后的能力对比 + 一条明确的设计判断 |
| 10 | 反思与方法沉淀 | 展示自省与抽象能力 | 2 条方法局限 + 1 条核心判断 + 理论依据 |

> 页数可压缩：反思与方法沉淀可合成 1 页；成果不必单独成页（见下）。

## 三层区分法

**这是最常见的结构病**：第 5 页的「机会点」和第 6 页的「方案」看起来一模一样，读者会觉得你重复讲了两遍。

### 诊断标准

如果**把两页并排放在一起，读者分不清差别** → 层级没拉开。

### 正确的三层

| 层 | 回答什么 | 抽象度 | 句式特征 | 例子 |
|---|---|---|---|---|
| **痛点** | 现在哪里有问题 | 现象 | 描述现状 | 每天要根据盘点计划计算库位数量，再逐个手动勾选 |
| **机会点** | 这揭示了什么设计机会 | **判断 / 方向** | 一句话原则，可迁移 | **把重复的机械计算交给系统，人只保留必须由人做的业务判断** |
| **方案** | 具体怎么设计 | 机制 / 交互 | 含具体做法、字段、流程 | 组长圈定范围 → 算法算数量 → 组长复核下发 |

### 机会点写法对照（改写前 → 改写后）

| ❌ 写成了方案 | ✅ 写成判断 |
|---|---|
| 算法自动算出每天最少需下发的数量 | 把重复的机械计算交给系统，人只保留业务判断 |
| 算法自动分配，同时考虑件数与难度 | 用可计算的规则代替"靠人协调"，让公平不依赖个人判断 |
| 对库位路线做排序优化 | 既然顺序用户改不了，就由系统按"行走效率"来排，而不是按编号 |
| 在效率看板中增补指标，并新增进度看板 | 让问题从"靠人盯"变成"数据自己暴露" |
| 让系统记住人—库位的对应关系 | 让"人—库位"的对应关系由系统记住，不再占用人的记忆 |

**判断标准**：把这句话拿到**另一个项目**里，还成立吗？成立 → 是判断；不成立 → 还是方案。

### 数量关系

`N 个痛点 : N 个机会点 : M 个方案`，允许 `N > M`（多个痛点收敛成一个解决方案方向），
但**封面/概览页的数字必须与实际页面一致**。

## 方案页四段式

```
痛点  →  影响  →  方案  →  结果
```

| 段 | 写什么 | 注意 |
|---|---|---|
| 痛点 | 现状里具体哪几步难受 | 用动宾短语分条（"核算库位数量""逐个勾选库位"），不要整段叙述 |
| 影响 | 代价，最好带数字 | 这里出现的数字要与「结果」的基线一致 |
| 方案 | 怎么改，**以及为什么保留某些人工环节** | 一定要写"我为什么没有全自动" —— 这是判断力 |
| 结果 | 可量化变化 + 口径说明 | 正文"缩短约一半"；如口径特殊（不含某功能）必须加脚注 |

**方案页的高级写法**：加上「初稿方案 → 被否原因 → 最终方案」。三步迭代能让面试官看到真实设计过程，这比只展示结果有说服力得多。

## 反模式（不要写）

| 反模式 | 为什么不行 | 改法 |
|---|---|---|
| 框架自述 | "见下一页""为下一步埋下伏笔""按角色分层整合看板" | 全删。读者不需要看施工图 |
| 「要点」区块 | 把一句话再总结一遍 | 并进正文 |
| 只报成绩不提局限 | 不可信 | 至少 2 条方法局限 |
| 成果单独一页只有两个数字 | 与方案页割裂、重复 | 分散到各方案页 |
| 用「结果」给痛点段结尾 | 与页面自己的「结果」块冲突 | 痛点段用「影响」 |
| 项目状态（已上线/未上线/搁置）随意出现 | 可能违反保密要求 | 明确问用户口径；7B 这类"搁置+复活"叙事要经用户确认才保留 |
| 主语用"本项目" | 稀释你的主导性 | 全文用「我」 |
