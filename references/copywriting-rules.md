# 文案规范

## 1. 主语：全文用「我」

作品集是**你个人的求职材料**，不是项目报告。

| ❌ | ✅ |
|---|---|
| 在这个项目里，**本项目**用情境构建法构建出一套情景 | 在这个项目里，**我**用情境构建法构建出一套情景 |
| 业务与产品的需求转向精细运营 | 我以第三方视角加入，目标是找出提升效率的机会点 |

写完全文搜一遍「本项目」「该项目」「团队」，除作者署名外都应该改掉。

## 2. 数据口径

| 场景 | 写法 |
|---|---|
| **正文** | 严谨、可核对：「耗时从 30~40 分钟降到约 15 分钟，缩短约一半」 |
| **可视化 / 封面** | 可概括：「效率提升约 1 倍」 |

**规则**：
- 同一份材料里，**正文与可视化的数字基线必须一致**（都基于同一个"改进前"值）。
- **封面承诺必须被兑现**：封面写"各提升约 1 倍"，就必须有方案页能对应到"组长"和"执行层"两个角色。
- **口径特殊必须加脚注**：例如"只统计下发需求本身的耗时，不含配置盘点策略"。
- **周期与月数要自查**：`2025.11 – 2026.07` 是 9 个月，`2025.09 – 2026.06` 是 10 个月。写了"9 个月"就核对日期跨度。

## 3. 术语表（先定，再写）

开工时先列出本项目的**角色名、阶段名、功能名**，全文只用一套。

| 类型 | 本项目示例 | 易错点 |
|---|---|---|
| 角色 | 盘点员 / 异常员 / 盘点组长 / 组员 | 「盘点员」与「组员」混用会让读者分不清是"某角色"还是"全体" |
| 阶段 | 需求来源 / 任务下发 / 任务分配 / 任务执行 / 任务评价 | 一处改名必须全文替换 |
| 方法 | 情境构建法 | 不要写成"情境构建""场景构建法" |
| 表单记法 | 人与物的交互 | 不要用「人×物」这类需要解释的记法 |

**内部角色名第一次出现要带功能解释**，否则外部读者看不懂：
> ✅「优先级最高的异常盘点与盘点复盘，改由**异常员**（专门处理异常盘点的角色）统一承接」

**改名流程**（血的教训）：
1. `grep` 全仓搜索旧词，列出所有命中文件（**包括历史文案 md**）
2. 确认哪些该改、哪些不该改（阶段名 vs 方案名可能不同）
3. 逐个替换后**再搜一次确认命中数为 0**
4. **不要凭印象替换** —— 曾经把用户从没改过的「任务分配」自作主张换成「任务领取」，污染了两个文案文件

## 4. 保密口径（必须先问）

不同公司要求不同，**不要在没问的前提下自己决定**：

| 项 | 要问什么 |
|---|---|
| 项目状态 | 能否出现「已上线 / 未上线 / 预发 / 搁置」 |
| 业务数据 | 真实数据能否脱敏后使用 |
| 截图 | 是否需要遮盖库位号、货品编码、员工姓名、身份证/手机号 |
| 公司名 / 系统名 | 能否写真实名称，还是用代称 |

> 注意有一类内容**看似是状态、其实是加分项**：「上线后有真实数据」比「设计了一个方案」更有说服力。
> 所以不要一刀切删除，问清楚再定。

## 5. 句式规范

| 类型 | 要求 |
|---|---|
| 痛点 | 动宾短语分条：「核算库位数量」「逐个勾选库位」；不要写成一段叙述 |
| 影响 | 一句话讲代价，尽量带数字 |
| 机会点 | 一句判断（见 narrative-structure.md 三层区分法） |
| 方案 | 讲清"改了什么 + 为什么保留某些人工环节" |
| 结果 | 数字 + 变化方向 + 口径脚注 |

## 6. 写完必须做的两项自检

### ① 重复段落检测（复制粘贴错误的唯一防线）

本项目曾把一条说明**原样复制**到另一个小标题下：「要经真实校准」的正文和「源于真实事实」一字不差，
导致"校准"完全没有解释。**这种错误肉眼极难发现。**

写完后按 ≥14 字的长句去重，凡在同一页出现两次即报警：

```bash
python3 scripts/extract_svg_text.py <目录> --dup-only
```

### ② 逻辑自洽检测

- 页面上每一句**结论性的话**，都要能被页面上的**数据或标注**支撑。
  反例：「越往后，越依赖人工完成」，但五个阶段里最后一个标的是「系统自动」。
- 一句话里出现数量（"共 3 处"）时，数一遍页面上是不是真的 3 处。

## 7. 数据验算（交付前必做）

**每一个百分比都要用首尾数字反推一遍。**

| 指标 | 首 → 尾 | 标签 | 验算 |
|---|---|---|---|
| 流失数量 | 100 → 17 个/日 | 减少 83% | (100−17)/100 = 83% ✅ |
| 退货暂存单量 | 1,000 → 14,000/日 | 提升 1300% | (14000−1000)/1000 = 1300% ✅ |
| 覆盖率 | 48% → 51% | 提升 3pp | 51−48 = 3pp ✅（**不是 +3%**）|

**常见错误**

- 数字与标签错配（1,000 → 14,000 却写 +140%）→ 反推一下就知道
- 百分点写成百分比（48%→51% 是 +3pp）
- 基线取错（用半年前的数字当基线，会被问"为什么不计项目期间"）
- **纯文本提取会把左右列串行** → 数据页务必按坐标（x, y）复原父子关系再判断

## 8. 归因规范

- 有大促 / 季节性 / 业务交接时，**明确写"不能简单归因于本功能"**
- 多个指标一起涨时，**只留一个最硬的**当成果，其余不写
- 业务线中途交接给别的团队时，写清"截止我交接前"的时间边界

## 9. 排版一致性（设计作品集的门面）

| 项 | 规范 |
|---|---|
| **引号** | 中文正文统一「」。**检查是否有 ASCII 直引号 `"` 混入** |
| **中英文空格** | 与用户确认规则后全文统一。常见约定：<br>· 数字 + 中文单位 → **加空格**（`2 名` / `12 份` / `1200 单/日`）<br>· 日期 → **不加**（`2022年8月`）<br>· 百分比 → **不加**（`83%`）<br>· 纯英文 → **不加**（`SUS系统` / `BD不接电话`） |
| **日期漏字** | 扫一遍 `\d{4}年\d+(中旬\|下旬\|上旬)` —— 常见漏「月」 |
| **括号** | 中文语境用全角（）；半角 `( )` 会显得细、间距不对 |

> 这三项都能脚本化扫描，命令见 [review-checklist.md](./review-checklist.md)。
