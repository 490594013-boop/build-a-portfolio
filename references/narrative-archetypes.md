# 叙事原型库

拿到项目材料后，先用这里的原型生成 **2–4 条候选叙事**，让用户选一条。

---

## 七个原型

### ① 方法先行型 ·「没有条件，就造方法」

| | |
|---|---|
| **一句话** | 在拿不到关键信息的情况下，我自造了一套可复用的方法 |
| **张力来源** | 约束 vs 产出：信息缺失，但方案必须成立 |
| **六段** | 问题（信息缺口）→ 方法（我造的方法）→ 应用（方法怎么用）→ 成果（数据）→ 复盘（方法的局限）→ 沉淀（方法的可迁移性） |
| **最需要** | 一套能被说清的、有命名的方法；最好有"为什么它不是拍脑袋"的论证 |
| **适合** | 无法调研 / 跨地域 / 跨界进入的项目；投方法论岗、策略岗 |
| **坑** | 方法说得玄、落不到具体决策；方法比成果讲得多 |

### ② 调研驱动型 ·「先搞清楚用户到底是谁」

| | |
|---|---|
| **一句话** | 通过线下/用户研究，把"用户是谁、什么最痛"从模糊变成确定 |
| **张力来源** | 假设 vs 事实：团队以为的用户 ≠ 真实的用户 |
| **六段** | 问题（业务下滑/目标转变）→ 方法（定量+定性双轨）→ 应用（研究结论怎么改产品）→ 成果 → 复盘（样本与偏差）→ 沉淀（研究如何改变决策） |
| **最需要** | 真实的一手材料：走访照片、问卷、访谈记录；**研究结论要能改变某个具体决策** |
| **适合** | 有实地调研、用户研究的 B 端 / C 端项目 |
| **坑** | 只报"调研发现了 X 个问题"，不说"因此我们改了 Y" —— 研究变成了展示，不是驱动 |

### ③ 约束突破型 ·「硬约束下重新定义问题」

| | |
|---|---|
| **一句话** | 面对一条"不能做"的红线，我把业务重新定义成能做的样子 |
| **张力来源** | 想做 vs 不能做：合规 / 技术 / 组织限制 |
| **六段** | 问题（业务缺口）→ 约束（红线是什么）→ 突破（重新定义的关键一步）→ 应用（落地设计）→ 成果 → 复盘（妥协的代价） |
| **最需要** | 一条清晰的、真实存在的约束；一次**"重新定义"**而非"绕过"的动作 |
| **适合** | 金融、医疗、物流等强合规行业；B 端项目 |
| **坑** | 写成"我们绕过了限制"（不专业、有风险）；或把约束写成抱怨 |

### ④ 迭代修正型 ·「上线就被现实打回」

| | |
|---|---|
| **一句话** | 第一版上线后，真实反馈推翻了假设，我用很短的周期改对了 |
| **张力来源** | 设计意图 vs 现场现实 |
| **六段** | 问题 → 方案（第一版）→ 现实的反馈（具体、扎心）→ 修正（第二版）→ 成果 → 复盘（为什么会想错） |
| **最需要** | **具体的、可引用的现场反馈**；一个短线迭代周期（几周内） |
| **适合** | 有上线后数据/反馈的项目；投重视落地的团队 |
| **坑** | 把第一版写成"明显有问题"（显得不专业）；或只说"改好了"，不说**为什么当初想错** |

### ⑤ 数据优化型 ·「把一个数字从 A 提到 B」

| | |
|---|---|
| **一句话** | 用数据定位瓶颈，逐项优化，把核心指标提上来 |
| **张力来源** | 现状指标 vs 目标指标 |
| **六段** | 问题（指标卡在哪）→ 归因（拆解瓶颈）→ 方案（逐项对症）→ 成果（指标变化）→ 复盘（哪些没提上去）→ 沉淀（可复用的优化路径） |
| **最需要** | **干净可信的数据**；能说清"哪个动作带来哪一部分提升" |
| **适合** | 增长、转化、效率类项目 |
| **坑** | 数据不验算（百分比对不上）；把多因素结果全归给自己 |

### ⑥ 协作博弈型 ·「在多方目标之间找平衡」

| | |
|---|---|
| **一句话** | 设计不只是画界面，是在法务、运营、技术、用户之间找那条能落地的线 |
| **张力来源** | 各岗位目标冲突 |
| **六段** | 问题 → 各方诉求（谁要什么）→ 冲突点（哪里打架）→ 我的解法（怎么让各方接受且用户能懂）→ 成果 → 沉淀（协作方法） |
| **最需要** | 真实的冲突案例（例：法务给的免责文案用户看不懂）；**具体到某一次沟通** |
| **适合** | 大厂跨团队项目；投需要推动力的岗位 |
| **坑** | 变成"吐槽合作方"；没有说清自己的作用 |

### ⑦ 能力前瞻型 ·「新技术该用在哪，不该用在哪」

| | |
|---|---|
| **一句话** | 面对 AI 等新能力，我判断的不是"能不能用"，而是"该不该用" |
| **张力来源** | 技术热度 vs 问题本质 |
| **六段** | 问题 → 旧方案的天花板 → 新能力的适配点 → 应用 → 成果/边界 → 沉淀（选择能力的标准） |
| **最需要** | 一条明确的**判断标准**（例：按问题性质选能力，而不是按技术新旧） |
| **适合** | AI 应用、新交互形态类项目 |
| **坑** | 写成"我们也用了 AI"；没有边界判断，显得跟风 |

---

## 如何组合

一个项目通常同时具备 **2–3 个原型**。做法：

1. **选一个当主原型** —— 决定开头和结尾怎么讲
2. **选一个当副原型** —— 决定中间最有说服力的 2–3 页
3. 其余弱化，不要都讲

> 例：某 B 端项目 = 主「调研驱动型」+ 副「约束突破型」+ 结尾「迭代修正型」

## 候选方案的生成模板

对同一份材料，用不同主原型能排出**完全不同的作品集**。给用户时要写清差别：

```
【方案 A · 调研驱动型】把"用户是谁"钉死
一句话主线：通过线下调研把目标用户从"所有代收点"收敛到"兼职代收点"，
           并据此推翻原有的功能优先级。
强调：研究方法的严谨性 + 结论如何改变决策
弱化：合规改造的技术细节
需要：走访照片、SUS 数据、两类站点画像
适合：投用户研究 / 策略岗

【方案 B · 约束突破型】没有牌照怎么把业务做成
一句话主线：在没有物流资质的红线内，用「退货暂存」重新定义业务边界，
           把一条"不能做"的链路做成能落地的方案。
强调：重新定义问题的那一步
弱化：调研过程
需要：合规限制的确切表述、法务/公关的确认过程
适合：投 B 端 / 强合规行业

【方案 C · 迭代修正型】上线一周被现实打回
一句话主线：第一版上线 1 周就暴露三个现场问题，用 2 周迭代修正，
           最终把单量从 1,000 做到 14,000/日。
强调：真实反馈 + 快速修正
弱化：前期调研
需要：上线后的真实反馈记录、两阶段的对比数据
适合：投重视落地与执行的团队
```

**关键**：三条方案的**开头、主角、结尾都不一样**，用户一眼能选出自己想要的那条。

## 反面例子（这些不算"不同方案"）

| 假方案 | 为什么不行 |
|---|---|
| A：讲调研；B：讲调研+方案 | 只是加了内容，没换角度 |
| A：强调用户价值；B：强调业务价值 | 换措辞，结构一样 |
| A：详细版；B：精简版 | 是篇幅差异，不是叙事差异 |

> 判断标准：**如果两条方案的页 1 和页 18 讲的是不同的事，才算不同方案。**
